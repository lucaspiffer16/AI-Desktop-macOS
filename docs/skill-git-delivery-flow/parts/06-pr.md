## PR formal obrigatório por etapa

Toda promoção entre ambientes exige PR formal com `gh pr create`.

Fluxos suportados:

- `feature/*` ou `bugfix/*` -> `homolog`
- `feature/*` ou `bugfix/*` -> `staging`
- `staging` -> `homolog` (sincronização de base quando aplicável)
- `staging` -> `main`
- `hotfix/*` -> `main`

## Regra geral

- PR para `homolog` valida a branch em ambiente integrado
- PR para `staging` promove somente itens já aprovados em `homolog`
- PR de `staging` para `main` publica a release oficial
- PR de `hotfix` para `main` corrige produção sem depender de `staging`

## Promoção para homolog

Após validações verdes e push confirmado:

- criar PR com base `homolog`
- manter título e corpo no idioma escolhido
- atualizar comentário da issue com o link do PR e status dos checks

Gate adicional quando branch nasceu de `staging`:

- validar alinhamento entre `homolog` e `staging` antes de abrir PR da feature
- se houver desalinhamento relevante, abrir PR formal `staging` -> `homolog` antes do PR da feature
- somente após esse alinhamento abrir PR da feature para `homolog`

Comando de referência:

```bash
gh pr create --base homolog --title "<titulo>" --body-file "/tmp/pr-body.md"
```

## Promoção para staging

Esta etapa só pode ocorrer depois de:

- validação em `homolog`
- confirmação explícita do desenvolvedor
- comentário nas issue(s) registrando essa aprovação em primeira pessoa

Regras:

- não promover diretamente `homolog` para `staging`
- abrir novo PR da mesma branch de trabalho para `staging`
- sem confirmação explícita do desenvolvedor, bloquear a promoção

## Sincronização staging -> homolog

Quando `homolog` precisar receber o mesmo ponto-base de `staging`:

- usar PR formal com base `homolog` e head `staging`
- registrar no corpo do PR que a etapa é de sincronização de base

Comando de referência:

```bash
gh pr create --base homolog --head staging --title "sync: align homolog with staging base" --body-file "/tmp/pr-body.md"
```

Comando de referência:

```bash
gh pr create --base staging --title "<titulo>" --body-file "/tmp/pr-body.md"
```

## Release para main

Para publicar release:

- usar PR de `staging` para `main`
- garantir que `staging` contenha apenas itens aprovados
- criar tag em `main` após merge autorizado

Comandos de referência:

```bash
gh pr create --base main --head staging --title "release: <versao>" --body-file "/tmp/pr-body.md"
gh pr view --web
```

## Hotfix para main

Para incidente crítico:

- usar PR de `hotfix/*` para `main`
- não depender de `staging`
- sincronizar a correção com `staging` e `homolog` depois do merge em `main`

Comando de referência:

```bash
gh pr create --base main --title "hotfix: <titulo>" --body-file "/tmp/pr-body.md"
```

## Regra de aprovação explícita

- PR para `staging` exige aprovação explícita do desenvolvedor no chat
- antes de criar esse PR, registrar nas issue(s) o comentário de aprovação em primeira pessoa
- PR para `main` no fluxo de release também exige aprovação explícita do usuário

## Regras operacionais

- PR formal sempre
- se existir issue associada e o fechamento for apropriado na etapa final, incluir `Closes #123` no corpo
- não fechar PR via CLI, exceto no fluxo de release autorizado com base em `staging`
- proibido merge automático
- merge somente após aprovação explícita do desenvolvedor ou do usuário, conforme etapa
- a mesma branch pode abrir primeiro PR para `homolog` e depois PR para `staging`
- quando houver stacked branch, declarar dependência explícita no PR (`Depends on #<PR-A>`)

## Template base obrigatório de PR

Copiar e preencher no corpo do `gh pr create`:

```md
## Contexto

Descreva o problema/oportunidade que motivou esta entrega.

## Objetivo

Descreva o resultado esperado desta mudança.

## Destino do PR

`homolog` | `staging` | `main`

## Escopo entregue

-
-

## Critérios validados

-
-

## Validações executadas

- [ ] lint
- [ ] testes
- [ ] build
- [ ] `npm run build` (quando aplicável)
- [ ] `docker build .` (quando aplicável)
- [ ] segurança: vulnerabilidades de dependências
- [ ] segurança: SAST (quando aplicável)
- [ ] segurança: varredura de segredos

## Aprovação para promoção

- [ ] validado em `homolog` (quando aplicável)
- [ ] aprovado explicitamente pelo desenvolvedor para `staging` (quando aplicável)

## Riscos e rollback

- **Riscos:**
- **Plano de rollback:**

## Evidências

Inclua logs, prints ou saídas relevantes para comprovar o comportamento.

## Vínculo com issue

Use o fechamento automático quando aplicável.

Exemplo:

`Closes #123`

## Checklist

- [ ] branch de trabalho usada (sem commit/push em `main`, `homolog` ou `staging`)
- [ ] PR segue o idioma combinado no chat
- [ ] conteúdo segue este template
```

## Proteções obrigatórias no repositório

Configurar branch protection no servidor:

- bloquear push direto em `main`, `homolog` e `staging`
- exigir PR para merge
- exigir checks obrigatórios verdes
- exigir pelo menos uma aprovação
